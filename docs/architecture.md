# Architecture

## Components

The application is organized into small modules so that AI interaction, validation, permissions, storage, and audit responsibilities remain separate.

- `app/main.py` — command-line/application entry point and coordination. It presents the final outcome; it must not bypass tool validation or approval.
- `app/agent.py` — Gemini integration using `google-genai`; sends user context and typed tool declarations, receives model responses/tool requests, and handles provider-facing errors. Model output is untrusted.
- `app/schemas.py` — Pydantic schemas for tool arguments and related validated data. Required fields and supported values are enforced here.
- `app/tools.py` — Python implementations of the four support tools. Each validates inputs and returns explicit success or failure outcomes; SQLite-backed work is delegated to storage.
- `app/permissions.py` — permission and approval checks for consequential actions. An AI tool request cannot satisfy the human-approval requirement.
- `app/storage.py` — SQLite connection/schema and ticket persistence and lookup, including idempotent ticket creation.
- `app/audit.py` — records tool requests, approval decisions, successes, and failures without secrets.
- `app/config.py` — loads configuration, including Gemini settings, from environment variables; never hard-code or log credentials.
- `streamlit_app.py` — optional user interface that calls the same safe application/tool flow; the interface must not bypass validation or permissions.
- `tests/` — automated checks for schemas, tools, permissions, idempotency, and agent/provider behavior.
- `docs/` — specification, acceptance criteria, and this architecture overview.

## Request-to-response flow

1. **Receive request:** `main.py` (or the Streamlit interface) receives a user's request and passes it to `agent.py`.
2. **Ask Gemini:** the agent sends the request and available typed tool declarations using `google-genai`. Provider configuration and availability are not assumed. Errors such as timeouts and rate limits are handled as failures.
3. **Interpret tool request:** if the model requests a tool, the application records the request for audit. The request is untrusted data and is not permission to act.
4. **Validate in Python:** `tools.py` validates the arguments against the corresponding Pydantic schema in `schemas.py`. Missing, malformed, or unsupported values stop the flow before execution and are logged as failures.
5. **Check permission:** for consequential actions, `permissions.py` checks application-controlled permission state. In particular, a simulated email remains pending until a human explicitly approves it. Text generated by the model cannot approve it.
6. **Execute safely:** after validation and any required approval, `tools.py` calls the appropriate operation. Ticket creation and status lookup use `storage.py` and SQLite. Ticket creation uses the idempotency key to avoid duplicates on retries. Email execution only records/returns a simulation result and never sends real email.
7. **Audit result:** `audit.py` records the outcome—success, failure, pending approval, or approval/rejection—without API keys or other secrets. Failures are not converted into successes.
8. **Return final response:** the application reports the actual outcome. It distinguishes a completed action from an action awaiting approval, a rejected action, a missing ticket, or a provider/validation/storage failure. It only claims success after the operation succeeds.

## Trust boundaries and invariants

- **Gemini is not trusted to validate, authorize, or attest to execution.** Python schemas and permission checks are authoritative.
- **Approval is external to the AI request.** The application must obtain explicit human approval before the simulated email action executes.
- **Database state is authoritative for tickets.** Status is read from SQLite, not generated or guessed by the model.
- **Idempotency protects retries.** The same key refers to the same ticket-creation operation and must not create a duplicate.
- **Email remains simulated.** No real delivery service or network send is part of this design.
- **Secrets remain configuration, not source.** The example environment file uses blank placeholders; logs and errors must not reveal secret values.

Exact schema fields, priority values, status labels, database migration strategy, approval UI details, and Gemini model selection remain implementation decisions and must be fixed consistently before the corresponding behavior is tested.
